# JARVIS Voice Assistant — Troubleshooting Notes

## 1. Project Overview

**Project:** JARVIS — Python Voice Assistant

**Technologies used:**
- Python
- SpeechRecognition — captures and recognizes voice commands
- Google Speech Recognition API — converts speech into text
- pyttsx3 — initial text-to-speech implementation
- Windows SAPI (Speech API) — final speech output implementation
- PyWin32 (`win32com.client`) — interfaces with Windows COM components
- Requests — fetches news using NewsAPI
- Webbrowser — opens websites
- Custom `musicLibrary.py` — stores song links

## 2. Issue 1: Python 3.14 Compatibility and C++ Compiler Problem

**Problem:**
- Initially, I was using Python 3.14.3.
- Some dependencies required by my voice assistant, particularly those involving native extensions, did not install or work properly in my environment.
- I did not have a C++ compiler installed, which made compiling certain packages from source difficult.

**Solution I implemented:**
1. Identified Python version and dependency compatibility as potential causes.
2. Downgraded Python from 3.14.3 to Python 3.12.3.
3. Configured my project to use Python 3.12.3.
4. Installed the required packages in the project environment.
5. Verified that the application could run.

**Result:** The project dependencies worked correctly after the version change, and I could proceed with voice recognition and assistant functionality.

**Technical learning:** Python package compatibility depends on the Python version and the availability of precompiled wheels. A C++ compiler is not always required; using a compatible Python version with prebuilt wheels can avoid compiling native extensions locally.

## 3. Issue 2: JARVIS Spoke Only Once

**Problem:**
- JARVIS successfully spoke the initial message, `"Initializing Jarvis..."`.
- Subsequent calls to `speak()`, including the wake-word response `"Yes"`, printed messages in the terminal but produced no audible output.
- This made the assistant appear to work in the terminal while failing to respond verbally.

**Initial implementation:**

```python
import pyttsx3

engine = pyttsx3.init()
engine.setProperty('rate', 175)

def speak(text):
    print(f"[JARVIS]: {text}")
    engine.say(text)
    engine.runAndWait()
```

**Troubleshooting steps I performed:**

1. Added print statements inside `speak()` to verify that the function was being called.
2. Tested multiple consecutive messages outside the microphone loop.
3. Confirmed that Python executed both speech calls without hanging.
4. Reinitialized the `pyttsx3` engine for each message to test whether reusing the engine caused the problem.
5. Changed the initialization from `pyttsx3.init('sapi5')` to `pyttsx3.init()`.
6. Tested Windows' built-in speech engine directly through PowerShell.
7. Confirmed that PowerShell successfully spoke multiple consecutive messages, narrowing the issue to the Python speech-output implementation rather than general Windows audio playback.

## 4. Final Solution: Use Windows SAPI Directly

Since the `pyttsx3` approach continued to fail, I switched to Windows' native Speech API through PyWin32.

**Step 1 — Install the dependency**

```powershell
.\.venv\Scripts\python.exe -m pip install pywin32
```

**Step 2 — Import the Windows COM interface**

```python
import win32com.client
```

**Step 3 — Create a speech synthesizer and update the function**

```python
speaker = win32com.client.Dispatch("SAPI.SpVoice")

def speak(text):
    print(f"[JARVIS]: {text}")
    speaker.Speak(str(text))
    print("Finished speaking:", text)
```

**Step 4 — Test consecutive messages**

```python
speak("First message")
speak("Second message")
speak("Yes, how can I help?")
```

**Why this approach?**
- `SAPI.SpVoice` accesses Windows' native speech synthesis interface.
- `speaker.Speak()` sends text directly to the Windows speech engine.
- The call is synchronous by default, so it waits for the current utterance to finish before returning.
- This bypasses the `pyttsx3` wrapper and tests speech output through a different Python interface.

**Important:** This was the solution I implemented to address the issue. The exact underlying cause of the `pyttsx3` behavior was not conclusively identified.

## 5. How the Wake-Word System Works

1. The microphone captures audio using `SpeechRecognition`.
2. `recognize_google()` converts the recorded speech into text.
3. The program checks whether the recognized text equals `"Jarvis"`.
4. If the wake word matches, `speak("Yes")` provides an audible acknowledgement.
5. The assistant listens again to capture the user's actual command.
6. `processCommand()` checks the command and performs the corresponding action.
7. Depending on the command, JARVIS opens a website, plays a song, or fetches news headlines.

**Answer:**

I switched to Python 3.12.3 and configured the project environment so the required dependencies could run.

Based on that result, I switched from `pyttsx3` to Windows SAPI directly using PyWin32. This allowed me to access the native Windows speech interface and avoid the wrapper that was causing problems in my setup. The experience taught me to isolate components, test dependencies independently, and troubleshoot systematically instead of changing multiple parts of the application at once."

- **Python compatibility:** Python 3.12.3 was used after encountering dependency issues with Python 3.14.3.
- **Debugging method:** Used logs, isolated tests, and a PowerShell speech test to narrow down the issue.
- **Root cause:** The exact cause of the original `pyttsx3` playback behavior was not confirmed.
